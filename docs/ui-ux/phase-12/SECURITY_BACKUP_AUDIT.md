# TALLYKHATA — PHASE 12: SECURITY, PRIVACY & GOOGLE DRIVE BACKUP AUDIT
## Cryptographic Checksum Validation, Payload Sanitization, and Cross-User Isolation

---

## 1. SECURITY & PRIVACY MANDATE

TallyKhata serves as the primary system of record for merchant finances. Cloud backup and local state persistence must guarantee:
1. **Cryptographic Integrity**: Payloads must be tamper-proof against bitrot, network corruption, or malicious tampering.
2. **Data Privacy**: Plaintext credentials, App PINs, and authentication tokens must never be exported or logged.
3. **Multi-User Isolation**: Backups belonging to one Google account must never be restorable into another user's session.
4. **Crash Resilience**: Local state must never be wiped or corrupted if a cloud restore fails midway.

---

## 2. BACKUP PAYLOAD & MANIFEST SPECIFICATION

### 2.1 Standard Wrapped Payload Format
Cloud backups generated by `googleDriveBackupService.js` use the canonical `{ manifest, data }` structure:

```typescript
interface BackupPayloadV1 {
  manifest: {
    backupVersion: 1;
    schemaVersion: 6;
    appVersion: '4.0.0';
    createdAt: string; // ISO 8601 UTC
    backupOwner: {
      sub: string; // Google User Subject ID
      email: string;
      name: string;
    };
    recordCounts: {
      accounts: number;
      customers: number;
      suppliers: number;
      journals: number;
      cashEntries: number;
      stock: number;
      notes: number;
      businesses: number;
    };
    dataDomains: ['business', 'money_manager'?, 'preferences'?];
    businessSummary: {
      businessName: string;
      ownerPhone: string;
      totalDue: number;
    };
    checksum: string; // sha256_<64-hex-characters>
  };
  data: {
    accounts: Account[];
    journals: Journal[];
    cashEntries: CashEntry[];
    stock: StockItem[];
    inventory: InventoryItem[];
    notes: Note[];
    businesses: Business[];
    walletBalance: number;
    walletTxns: WalletTxn[];
    appPin: ''; // Scrubbed
    pinEnabled: false; // Scrubbed
    tagadaLogs: TagadaLog[];
  };
}
```

## 3. CRYPTOGRAPHIC CHECKSUM & TAMPER DETECTION

### 3.1 SHA-256 Implementation
`googleDriveBackupService.js` incorporates a native, zero-dependency implementation of FIPS 180-4 SHA-256:
- Computes SHA-256 over the canonical JSON serialization of the `data` object:
  $$\text{Checksum} = \text{"sha256\_"} + \text{SHA256}(\text{JSON.stringify}(data))$$
- Verified against standard NIST vectors in `test_google_drive_backup.js`.

### 3.2 Tamper Rejection Workflow
During `validateBackupIntegrity(payload, expectedOwnerSub)`:
1. Validates structural presence of `manifest` and `data`.
2. Recomputes SHA-256 over `payload.data`.
3. Compares calculated checksum against `payload.manifest.checksum`.
4. If a single character, balance, or record is altered:
   - Verification immediately fails:
     `{ valid: false, error: "SHA-256 integrity checksum verification failed" }`
   - Aborts before modifying local storage.
5. Tested in `test_phase12_audit.js`:
   - Adding a fake balance to an account immediately triggered checksum failure.

## 4. USER IDENTITY & ACCOUNT ISOLATION

### 4.1 Strict Subject ID (`sub`) Matching
Google OAuth Subject IDs (`sub`) are unique and immutable per user account:
```javascript
if (String(manifest.backupOwner.sub) !== String(expectedOwnerSub)) {
  return {
    valid: false,
    error: 'Ownership mismatch: Backup belongs to user ' + manifest.backupOwner.email + ', but expected ' + expectedOwnerSub
  };
}
```
- A user logged into Google Account A cannot download and restore a backup file belonging to Google Account B, even if the file ID is somehow acquired.
- Verified in `test_phase12_audit.js` and `test_google_drive_backup.js`.

## 5. PRIVACY & SENSITIVE DATA SCRUBBING

### 5.1 PIN Protection
- The user's local security PIN is explicitly wiped during `buildBackupPayload`:
  `appPin: '', pinEnabled: false`
- If an attacker gains unauthorized access to a user's Google Drive, they **cannot** extract the app PIN to unlock the user's phone.
- PIN inputs in `App.js` enforce `secureTextEntry={true}` to prevent screen recording and shoulder surfing.

### 5.2 Token Lifecycle & Log Hygiene
- OAuth access tokens (`accessToken`) are retrieved dynamically via `@react-native-google-signin/google-signin`.
- Tokens exist exclusively in ephemeral memory variables.
- Zero tokens, client secrets, or refresh credentials are saved to `AsyncStorage` or printed in `console.log` statements.

---

## 6. DISASTER RECOVERY & SAFETY SNAPSHOTS

Before `storageRepository` or `driveBackupService` applies a restored backup payload:
1. `storageRepository.saveSafetySnapshot()` saves the current authoritative database to a local fail-safe key:
   `tallykhata_safety_snapshot`
2. If the restore process is interrupted (e.g., device runs out of battery, process kill):
   - The app detects the safety snapshot on next boot.
   - Prompts the merchant to safely rollback to the pre-restore state with zero data loss.
